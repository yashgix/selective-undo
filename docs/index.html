Collaborative undo in Tilo: a design, a benchmark and three fixes in upstream's own

When several people edit the same thing, undo should take back your action and keep what others did since. I built and benchmarked that for Tilo's resource store. When the maintainers landed their own version of the core idea, I carried the same benchmark and tests over to their code. That found a 26-second slowdown in Store::undo (issue #5993, fixed in one function) and two cases where the revert leaves the wrong state: a counter step that is not taken back beside another author's, and a replaced map's old key that comes back. Both are repaired.

[ How undo works ]

The undo path in upstream today

Since dd0f8bbc37, Store::undo takes back an invocation by calling the history's revert for each document it changed. The revert finds the invocation, computes the inverse, decides per patch whether to write it or keep another author's value, and writes one change. The two findings below sit at two different points of this path.

[ Finding 1 · speed · issue #5993 filed ]

Where the 26 seconds go

Upstream's change made Store::undo take back an invocation by calling the history's revert in each document. Part of that revert, first_index_after, finds where an invocation sits in a document's history. It rebuilt the heads of every prefix, and each rebuild read all change metadata, so one undo cost time quadratic in the number of changes. The function predates the change, and the new undo put it on the path of every undo.

A history of changes. To find where the invocation sits, upstream rebuilt the heads of every prefix, rereading all earlier changes each time. The fix keeps the heads while it walks the history once. Shown with a small history, the measured times for large ones are in the race above.

Measured, all sizes

Two things stand out. Upstream's undo is much faster when the document was written in one change. When it was written in many, it grows with the square of the history: ten times more changes took about 96 times longer (272 ms to 26.0 s). With the repair, ten times more changes take about ten times longer.

Conditions. Release build, run alone, on a laptop under load (macOS storage services at 85 to 163% of a core, load average 5 to 7), so treat the absolute numbers as indicative. The old-store column was measured earlier on the same machine. The gap between 26 s and 0.6 s is far larger than that noise.

The repair

The heads of a prefix change in a simple way when the prefix grows by one change: that change's dependencies stop being heads, and the change itself becomes one. Keeping the set as the loop advances removes the repeated rebuilding. This is the whole change, in crates/core/resource-store/src/history/revert.rs:

- for i in 0..total {
-     let hs: HashSet<ChangeHash> = prefix_heads(doc, i).into_iter().collect();
-     if hs == after_set { return i + 1; }
- }
+ let mut heads: HashSet<ChangeHash> = HashSet::new();
+ for (i, meta) in doc.get_changes_meta(&[]).iter().take(total).enumerate() {
+     for dep in &meta.deps { heads.remove(dep); }
+     heads.insert(meta.hash);
+     if heads == after_set { return i + 1; }
+ }

The lookup returns the same index as before. In these measurements the cost grows about tenfold for ten times the changes.

[ Finding 2 · correctness · issue #5995 and pull request #5996 open ]

Two places where upstream's revert leaves the wrong state

I carried my revert, merge and counter scenario tests over to upstream's code (27 tests). 6 fail on unmodified main and none with the fix in revert.rs. My text and counter generator gates (1,000 seeded histories each) pass on upstream too, but every history in them has one author, so none puts a second person's step on the same counter. Press the buttons in order. The panels replay results recorded from the tests.

1. Undoing a counter increment does nothing once someone else changed the counter

Upstream main
With the fix

Increments add up, so Ben's −2 does not overwrite Ada's 5, and her 5 can be taken back without touching his −2. Upstream treats his change as an overwrite, reports the slot as kept and writes nothing. It needs a second author: on a plain document it fails whether his step comes later or at the same time, and with two synced stores (Ada in one, Ben in the other) Store::undo leaves 3. In one store where his step is simply the next invocation, Store::undo already gives −2, so that sequential case is fine. Tests: an_increment_is_taken_back_beside_another_authors_increment, a_concurrent_increment_by_another_author_is_kept and the two-store test undoing_a_counter_step_beside_a_peers_step_keeps_theirs. Tilo's counter app (apps/tl/counter/app.tl) uses this kind of field.

2. A replaced map's old key comes back

Upstream main
With the fix

The new map stays after the undo because Ben wrote inside it, and that part is right. But upstream writes the inverse of the replacement into it, and with it the older map's key k. Test: a_map_the_run_put_over_an_older_one_keeps_its_replacement_free_of_the_older_keys.

3. Reporting only: a list counter another author replaced or deleted

Undo correctly writes nothing and keeps their value, but reports 0 slots kept instead of 1. Nothing is lost, so I count this separately from the two above. Two tests cover it (a_list_counter_another_author_replaced_is_kept and ..._deleted_is_kept_and_nothing_is_written).

[ Original work · 20 to 23 Nov ]

This is the investigation and implementation from 20 to 23 Nov, on Tilo as it was then. The code is kept in historical/patch/. I kept it private while I prepared it, and Tilo landed its own version first. The numbers on this tab are for Tilo at commit 2fcb9946fe, not for today's main.

The problem, in Chat

Chat stores a message's reactions in one map. The old undo put the whole map back the way it was before Ada's reaction. That was empty, so Ben's reaction went too. Press the buttons in order. The panels show the old store undo, my undo, and what upstream's new undo does today.

This panel replays results recorded in tests, it is not a live system. Setup: two stores that sync, driven by the commands a Chat reaction sends. Upstream's undo never loses Ben's reaction, but when Ada's reaction created the map, her own undo does nothing. My undo removed hers exactly. On upstream it is a refinement, not data loss.

A benchmark for the property

One example is not enough, so a test generator builds 2,000 random histories of edits to maps, lists, nested objects, text and counters. For each one it undoes an edit and compares the result with a replay of the same history that never contained that edit. When no later edit depended on the undone one, the two must match. That applies to 1,300 of the histories.

My undo's one remaining case is a list-order choice: a restored list item goes back after its old neighbour, which is what Tilo's own test expects. Upstream's undo reports 0 on the same generator, which I ported to its new code layout.

The earlier performance journey

My first version of the undo took 33 s for one undo on a document with 10,000 items and 10,000 small changes. The store's undo at the time took 0.60 s, so it was about 55 times slower. Most of the time was in the first_index_after lookup that already existed in Tilo's revert. Making it a single pass brought my version to 0.19 s. It is the same repair that later fixed upstream's 26-second undo.

Median per undo, log-scale bars. "Store's undo then" is the store's undo at that time. Run on Tilo at 2fcb9946fe, with the machine busy (storage services 108 to 174% of a core, load 6 to 14), so indicative only.

What was built

  • Undo reuses Tilo's revert. An optional ContentUndo hook in the resource store, with the workspace service plugging in revert_changes. At the time the store sat below the collaboration crate, so the hook was injected. A multi-document undo is rolled back if a later document fails, and that rollback can itself fail.
  • Fixes in the revert itself that the new tests found: counters that several people increment, replaced maps, and the slow lookup.
  • A repair caught by Tilo's own test. My first rule for Chat took a block's own keys out of a block someone else had edited. Tilo's existing "undo the agent's work" test failed on a paragraph. I bisected it against upstream, removed the rule, and moved the Chat behaviour into a narrow store rule for flat maps. A review then found two edge cases in that rule (a concurrent write at the same entry, and a map holding an object), which I fixed.
  • Concurrent writes. Tests cover an entry another author writes later, and a concurrent write of the same value. A deliberately weakened guard fails exactly that test, so it tests write history and not value equality.
  • 86 new tests run by default, plus 7 measurements, with 1,000-seed gates in two actor modes.

[ How upstream evolved ]

How upstream evolved

On 24 Nov at 12:47 UTC the maintainers landed two commits. a6758222e2 moved the history engine, the revert and the undo log into the resource-store crate. dd0f8bbc37 made Store::undo take back an invocation by calling that revert in each document it changed, and removed the store's own old undo and its key copy. They did this independently: nothing of mine had been filed or shared.

Moving the history engine into the store removed the layering problem my hook worked around, so the hook was no longer needed. It confirmed the direction and gave me the code to test next. What was mine and what was theirs:

Adapting the work

  • Fetched upstream main (commit b06ae3fe8e, 4,158 commits past my base) and exported it as a separate offline build copy, reusing the compiled dependency cache.
  • Ported the generator and the latency test to the new layout (crates/core/resource-store). They use only the store's public API, so they ran against upstream's own Store::undo with no hook. The Chat probe needed one change: a stricter store now refuses changes for a type it has not declared, so the probe declares the type.
  • Ran them, found the 26 seconds, then applied only the one-pass lookup to upstream and re-measured and re-tested.
  • Checked the report before filing: duplicates on Tilo's Forgejo, whether main had moved, and that the reproduction test in the issue compiles.

Scope and limits

  • Chat reaction on upstream main. If Ada's reaction created the reaction map, Ben reacts, and Ada undoes, both reactions stay: nothing is lost, but Ada's undo does nothing. With an earlier reaction already in the map, it is exact. A small store rule for flat map fields made the first case exact in my original work. It is documented here and not proposed; it is a refinement, not data loss.
  • Automerge behaviour. Writing a value an entry already holds records no operation, so there is no later write for undo to protect. Two people creating the same fresh map at the same time is an Automerge conflict (one map wins), independent of undo.
  • My change's boundaries (original work). A person undoing an earlier edit still takes back their own later edit on that field. If another author wrote inside an object the action created, that object stays whole. A restored list item goes back after its old neighbour. The store rule cannot tell a flat attribute map from a flat collection without a schema. Windows with no workspace kept the old undo.
  • Measurement conditions. Timings come from a laptop under load, release builds without LTO. They show orders of magnitude and scaling.
  • Verification scope. Checks ran in an offline build copy of upstream, outside Tilo's own t build server. TECHNICAL.md lists what ran, on which commit, and what was left to Tilo's CI.
